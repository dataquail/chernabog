# 4. @chernabog/core is the binary's contract with every repo's flows

Status: accepted, 2026-10-28. Issue #163.

## Context

One binary runs every enrolled repo. Until now the loader pointed every
flow's `import "@chernabog/sdk"` at the binary's bundled copy, so the code a
repo ran was always the binary's, whatever its pin said. The SDK was two
things in one package: the contract (the flow shape, the durable primitives,
the service ports) and the library (`Implement`, `Review`, `Plan`, `Hybrid`,
prompts). Most of the churn was in the library, but since it shipped with the
binary it set the binary's support window: upgrading Chernabog for one repo
could make another `incompatible`.

## Decisions

1. **Two packages.** `@chernabog/core` is the contract: the flow shape and
   the hooks the daemon calls (`trigger`, `item`, `gate`, `stillValid`), the
   durable primitives (`activity`, `step`, `sleep`, `awaitSignal`, `gone`),
   the typed errors, the service ports, and the conventions the daemon itself
   acts on, whatever the flow: claims (`Claims`, including `branchFor`) and
   markers (`Markers`, the comment markers). `@chernabog/sdk` is the blocks a
   recipe is written from, over core's ports, and re-exports core, so a flow
   imports from one package.

2. **The binary provides core; each repo installs its own SDK.** The loader
   substitutes the binary's copies of `@chernabog/core` and `effect` (one
   `effect`, because `Schema` classes, fibers and `Context` don't work across
   two). Everything else, the SDK first, resolves from the snapshot's
   `node_modules`: `.chernabog/package.json` lists `@chernabog/sdk` in
   `dependencies`, and each snapshot installs it from the lockfile. Two repos
   on different SDKs run in one daemon.

3. **The binary decides by core alone.** The installed SDK's peer range on
   `@chernabog/core` is the repo's version fact. The binary runs the repo
   when a core it provides (`PROVIDED_CORE`, `src/kernel/core-support.value-object.ts`)
   satisfies the range, and refuses it as `incompatible` otherwise, saying
   which side to move. Flows that import `@chernabog/core` directly are also
   checked against the bundled core's exports before anything loads.
   `architecture.yaml` keeps `src/` out of the SDK's code (`daemon-reaches-no-sdk`),
   so the binary never depends on blocks it doesn't run.

4. **Core only grows within a major.** Core starts at 1.0.0 so that a peer
   range such as `^1.2.0` means what it says: every later 1.x satisfies it.
   - **Ports only grow.** Add a method; never change an existing one's
     signature or the errors it fails with. A shape that must change gets a
     new service key (`@chernabog/sdk/GitHub` beside `.../GitHub/v2`), and the
     binary keeps providing the old key as an adapter over the new one. The
     keys keep their `@chernabog/sdk/` prefix from before the split: a key is
     an identifier, not a package name.
   - **The durable primitives are frozen.** `activity`, `step`, `sleep`,
     `awaitSignal`, built-in signals and journal keys are what a run in
     flight resumes by: a wire protocol, not an API.
   - **The hooks the daemon calls are as fixed as the ports.**
   - **Claims' and markers' names and arguments are fixed** once a release
     holds them: the daemon releases a run's markers by name, from a newer
     binary than the one that held them.
   - **Removing or changing anything is a major.** A binary that wants to keep
     running the previous major's SDKs adds it to `PROVIDED_CORE` and keeps
     the adapters; one that drops a major is a major of Chernabog's own.

5. **Enforced, not just written down.** `packages/core/API.md` holds what
   `tsc` declares of core, regenerated by `bun run gen:core-api` and held
   current by a test, so every change to the contract is a diff a reviewer
   reads against these rules. CI's `published` job installs the oldest and
   the newest `@chernabog/sdk` on npm whose core range this branch provides,
   with the newest recipes for each, and loads every recipe under this
   branch's core.

6. **A run resumes against the tree it started from.** Each run records the
   `.chernabog/` tree it started from (`om_runs.config_tree`) and the core it
   started under (`om_runs.core_version`). A resumed run loads its flow from
   that tree's snapshot, extracting and installing it again if it's gone, so
   neither a merge to `.chernabog/` nor a move of the repo's SDK swaps the
   blocks under a run in flight. A binary resumes a run only when it
   provides that run's core major at that version or later.

## Consequences

- Upgrading Chernabog breaks a repo only when core's major moves past what
  the repo's SDK accepts, not whenever the blocks change.
- The blocks are each repo's business: `chernabog recipes upgrade` moves a
  repo to the SDK released with the binary, and the repo merges it when it
  chooses.
- Every repo needs a lockfile, since every repo now installs the SDK.
- Runs from before this change recorded the all-in-one `@chernabog/sdk` they
  started under; no core-providing binary resumes them, so they go to a
  person. Repos on the all-in-one SDK are `incompatible` until
  `chernabog recipes upgrade`. Compatibility starts with core 1.0.0.
- A block that reaches past core's ports into the binary's internals would
  break silently once blocks ship apart from the binary; the import rules on
  `packages/sdk/` keep it to core's entry, `effect` and `node:`.
