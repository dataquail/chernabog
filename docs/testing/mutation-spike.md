# Mutation testing spike (#575)

Part of epic #574. This tries StrykerJS on the two targets the issue names and answers its six questions with measured numbers. The throwaway configs, logs and raw reports are in `mutation-spike/` in the spike's worktree, uncommitted. The last section proposes the epic's remaining issues.

**In short:** StrykerJS 10 runs well under `bun test` through a community runner, `@hughescr/stryker-bun-runner`, which has per-test coverage, bail and incremental mode. Effect code needs nothing special. Both targets take under a minute cold and about 5 s incrementally on an M2 Max, so a nightly run of the whole proposed scope fits easily on a GitHub-hosted runner. Signal is high: 161 of the 188 survivors (86%) are real gaps, 10 (5%) are equivalent and 17 (9%) are noise. Two things matter more than the tool choice:

- **Which test files each module runs against.** The issue's narrow test selection left 33 mutants surviving that other focused tests do kill.
- **Timeouts are not reliable kills.** With slow engine tests in the selection, Timeout verdicts come from load, not from infinite loops.

## 1. Tool and runner

**StrykerJS runs against `bun test`.** No runner ships with Stryker itself, but two community ones exist:

- `@hughescr/stryker-bun-runner` 1.6.0 (October 2026, supports Stryker 9 and 10, Bun 1.4 or later), used here;
- `stryker-mutator-bun-runner` 0.4.0, last published July 2025, not tried.

The hughescr runner is a native runner:

- **Per-test coverage.** It follows each test through Bun's inspector, and a preload records which mutants each test reaches. A mutant then runs only its covering tests, in a fresh `bun test`, and bails at the first failure.
- **Incremental mode** works with it.
- **The repo's `bunfig.toml`** is copied with its `preload` (the ledger check) kept and `coverage` forced off.

Stryker's generic **command runner** works too. Here it ran `bun --config=mutation-spike/bunfig.mutation.toml test --bail --preload ./test/ledger-checked.preload.ts <files>` once for every mutant. It gave the same verdicts:

|                           | killed | timeout | survived + no coverage |
| ------------------------- | ------ | ------- | ---------------------- |
| progress, bun runner      | 216    | 3       | 88 + 84                |
| progress, command runner  | 216    | 3       | 172                    |
| catalogue, bun runner     | 276    | 1       | 100 + 76               |
| catalogue, command runner | 276    | 1       | 176                    |

The command runner can't tell survived from no coverage, has no incremental reuse by test, and was 1.5–1.8× slower (26 s vs 18 s, 89 s vs 49 s). The bun runner is the one to use.

That table is also the evidence that **the bun runner's coverage mapping is right**. It warns `Interior coverage gap detected … coverage key paired with inspector test from "test/effect-test.ts"` on every file that uses the `effect(...)` test helper, because the helper defines the test in `effect-test.ts`. The command runner has no coverage mapping to get wrong, and the verdicts match it mutant for mutant. `coverageAnalysis: "off"` with the bun runner also gave the same statuses for every mutant.

**Effect.** Stryker instruments with Babel, which parses the TypeScript, `Effect.gen` generators, pipes and `Schema` with no errors. No mutant was an Error or a CompileError. Stryker's typical failure points don't apply:

- **The `effect-tsgo` patch** applies to the lint toolchain (`effect-tsgo patch --oxlint`), which Stryker never loads.
- **No TypeScript checker was needed.** Bun doesn't type-check, and mutants run fast enough. With a checker, the runner needs `typescript` below 7; the repo's `typescript` is 5.9.3 (`@typescript/native` is the TypeScript 7 alias), and `bun add` raised no peer warning.

Mutant switching interacts with Effect in one way. Schema `ObjectLiteral` mutants (`Schema.Struct({...})` → `Schema.Struct({})`) are mostly invisible: in Effect 4, `Struct({})` passes every key through (`mutation-spike/struct-probe.ts`), so the mutant only changes behaviour on a malformed input (Q3, Q5).

**What nearly ruled the tool out:**

- **Sandbox vs workspaces.** Stryker's default sandbox symlinks `node_modules`, and `node_modules/@chernabog/{sdk,core}` are workspace symlinks to the real `packages/`. In a sandbox the tests would import the unmutated SDK, so every `packages/sdk` mutant would read as surviving or uncovered. **`inPlace: true` is required.** It is fine on a CI checkout, but it rewrites the working tree for the length of a run.
- **Slow tests turn into false Timeout kills.** See Q2.
- **Static mutants** (module-level constants, regexes, `Schema` definitions) run the whole selection each. They are 24% of the catalogue's mutants and 15% of progress's.
- Mutants killed only by a static failure leave an empty `killedBy` and re-run on every incremental run (8 in the catalogue). The runner warns about this; it is harmless.

The wider catalogue selection takes 9 minutes because it brings in engine tests that wait in real time. They take 39 s serially (net 18 s), against 1.7 s for the narrow five. With 8 workers on one machine, those runs overran Stryker's per-mutant timeout:

- The wide run scored 43 mutants Timeout, 31 of them static, and none with a hit-limit reason except 3.
- Re-running 19 of the mutants on three lines with `timeoutMS: 180000` and 4 workers took 156 s, and **6 that had been scored Timeout survived**: the RUN_ID anchors, the issue prefix, and Checking's key. Timeout counts as detected in Stryker's score, so these were false kills.

A nightly run needs a generous `timeoutMS`, or no real-time tests in a module's selection, and should report Timeout on static mutants as unverified.

**Extrapolating to GitHub-hosted runners.** The repo is public, so `ubuntu-latest` has 4 vCPUs and 16 GB. As a calibration, today's CI `unit` job ran `bun run test:unit` in 218 s (run 44920902503); the same command takes 142 s here, so CI is about 1.5× slower on a parallel workload. The runs here are CPU-bound, so I scale by CPU time over 4 workers:

| target             | estimated cold time on CI | estimated incremental time on CI |
| ------------------ | ------------------------- | -------------------------------- |
| progress           | ~30 s                     | ~10 s                            |
| catalogue (narrow) | ~2 min                    | ~10 s                            |

Both estimates exclude about 30 s of checkout and `bun install`.

The scope proposed in Q6 adds about 2,000 lines, roughly 1,000 to 1,200 mutants at the 0.5 mutants per line measured here, all on tests that run in under 2 s. That's another 3–5 minutes cold.

**A nightly cold run of the whole scope is about 10 minutes, and an incremental night under 2.** That holds as long as the slow engine tests stay out of the selections, or run with a large `timeoutMS` (which could take a cold catalogue run to 20–30 minutes). It is well within the 6-hour job limit, and could be split into one matrix job per module.

## 3. Signal

Every survivor of the narrow runs is classified in the tables below. I was strict: if a caller or a test could observe the change, it is a real gap. Two kinds of real gap are tagged because they matter for prioritising:

- _malformed-only_: a `Schema` mutant that differs only on input of the wrong shape;
- _cost only_: the result is the same, but there are extra GitHub requests.

"Wider selection" says what the wider test set made of each mutant: Killed (by which file), Survived, or Timeout. A Timeout there is unverified (Q2).

| target                                             | survivors | real gap      | equivalent  | noise       |
| -------------------------------------------------- | --------- | ------------- | ----------- | ----------- |
| progress (`progress.ts` + `progress-anomalies.ts`) | 88        | 71 (81%)      | 7 (8%)      | 10 (11%)    |
| catalogue (`ledger-check.ts` + `phases.ts`)        | 100       | 90 (90%)      | 3 (3%)      | 7 (7%)      |
| **total**                                          | **188**   | **161 (86%)** | **10 (5%)** | **17 (9%)** |

Inside the real gaps:

**Progress (71):**

- 17 are malformed-only;
- 4 are cost only;
- 7 are killed by the wider selection: `phase-announcer.test.ts` kills `makeRepoProgress`, and `ledger.test.ts` kills six of `parseSeen`'s regex mutants;
- `threads-setup.test.ts` would kill two more (`THREADS`, `THREADS_PATTERN`);
- 64 survive the wider selection.

**Catalogue (90):**

- 26 are killed by the wider selection (`adopted-ci`, `ci-park`, `document-park-ci`, `document-park-wait`, `plan-ci`, `resolve-conflicts-ci`, `epic-task-ci` and `adopt` tests);
- 30 were scored Timeout there and are unverified (6 re-checked and still survive);
- 34 survive it outright.

**No coverage (160 mutants).** These are mostly code the narrow selections never reach:

- all of `progressAnomalies`, which has **no unit test at all** (its only coverage is `parseSeen`, through `test/ledger.test.ts`);
- `phases.ts`'s park functions, which the park tests cover;
- `progress.ts`'s error paths that the threads fake never takes: 403/404 on commits, ref errors other than a ruleset's, a lost first-phase race.

With the wider selections, 76 and 19 remain.

### Real gap 1: a writer's second move from the same read returns its first (`progress.ts:179`)

```diff
 const isOwn = (record: PhaseRecord, transition: PhaseTransition) =>
   record.by === transition.by &&
-  record.phase === transition.to &&
+  true &&
   Equal.equals(record.from, fromPhase(transition));
```

`isOwn` is what lets "a retry find its own write". Without the phase check, the following happens:

1. Run A advances `pr-73` from review-asked to changes-asked.
2. Run A then advances again from the same read of review-asked, this time to approved, as a document's two branches or a buggy resume could.
3. The adapter returns the changes-asked record as success, instead of `PhaseMoved`.

The caller believes it recorded approved, and nothing was written. AGENTS.md's rule says the retry has to be _the same phase_: "Two advances by one writer from the same phase to the same phase are one write".

The contract (`test/progress-contract.ts`) tests these:

- a retry of the same move by the same writer ("a retried advance finds its own transition…");
- the same move by _another_ writer ("the same transition by another writer is a lost race");
- `decide`'s unit tests in `progress.test.ts` cover the same two plus a plain write.

None of them has the same writer, the same `from` and a different `to`, so the mutant passes all 63 tests. The probe test "one writer's second move from the same read, to another phase, is a lost race" (`probes.spike-test.ts`) passes on the code as it is and fails with the mutant applied by hand. The real tests pass with the mutant (89 pass across `progress.test.ts`, `test/progress.test.ts` and `phase-announcer.test.ts`). The case belongs in `progressContract`, so the in-memory fake and any hosted adapter are held to it too.

### Real gap 2: `observer:acknowledged` may record any transition (`ledger-check.ts:117`)

```diff
     if (observed.from === "same") {
-      return ofKind && Option.contains(record.from, record.phase);
+      return true;
     }
```

The ledger's tamper evidence (ADR 21, decision 5) lets a person's acknowledgement write only "the phase again": `from` equal to `to`. Under the mutant, a record by `observer:acknowledged` passes the check whatever the transition, for example `changes-asked -> approved` on a pull request. That is the one forgery the acknowledgement writer exists to prevent, and nothing notices.

`test/ledger.test.ts` "sabotage of address-review's record" forges an unknown writer, an undeclared run transition and an observer's undeclared transition. It never forges a record by `observer:acknowledged`. "a person's fix for an anomaly" only exercises a genuine acknowledgement, which passes either way.

The probe `Ledger.anomalyIn([], "pr-73", <changes-asked -> approved by observer:acknowledged>)` is Some on the code as it is and None with the mutant. The 105 tests of the five catalogue files all pass with the mutant applied. The same mutant also survives the 18-file wider selection.

### Also worth a look

- **The race tests don't race on the threads adapter** (`progress.ts:480`, `558`; mutants 297, 299, 300, 344). On this adapter, the contract's "of two first phases at once, exactly one wins" never reaches the 422 "Reference already exists" path. The fake answers synchronously, so the first fiber finishes before the second reads. The probe prints `["graphql ref", "POST …/git/commits", "POST …/git/refs", "graphql ref"]`: the second advance reads the first's record and loses before writing. The lost-race branch of `first`/`firstOrMiss` is NoCoverage. The fake needs a hook to interleave two writers, like `beforeNextAdvance` for later phases.
- **A retry that finds its own write writes again** (`progress.ts:608`, mutant 373). Skipping the short-circuit sends an orphan root commit, or a failing `createCommitOnBranch`, and then self-heals. The contract test says "writing nothing", but checks only the record. The probe that asserts the request log fails under the mutant.
- **The fake doesn't check what it's sent.** `split("/")` → `split("")` (owner "a", name "c") survives, as do an empty `EMPTY_TREE` and non-empty `parents`. `github-threads-fake.ts` ignores the GraphQL `owner`/`name` and the commit's tree and parents.
- **Lost races in the SDK are untested.** `catchTag("PhaseMoved")` → `catchTag("")` survives in both `Phases.record`'s retry loop (`phases.ts:291`) and `Phases.reconcile` (`phases.ts:506`), even against the 18-file selection. No test makes either lose a race.
- **Single-digit items everywhere.** `/^\d+$/` → `/^\d$/` in `kindOf` (`ledger-check.ts:83`) survives the narrow selection: under it `pr-73` has no kind, and its record goes unchecked. The narrow tests use `PULL = 7` and `ISSUE = 3`.

### Equivalent mutants, and why no behaviour changes

- **`progress.ts:325` (216, 217), `:338` (222), `:424` (262): the `seen` cache.** `read` and `readAll` query GitHub on every call either way. The cache only saves re-parsing a tip's message, and a re-parsed record equals the one cached: `at` comes from the same `committedDate`, and `data` round-trips through the `Data` trailer, which "reads back as the record it was written from" pins. No caller can tell a cached record from a re-parsed one; tests compare with `toEqual`, and no code compares records by identity.
- **`progress.ts:361` (234), `ledger-check.ts:144` (92): `() => ({})` → `() => undefined` inside an object spread.** `{ ...undefined }` and `{ ...{} }` produce the same object.
- **`progress.ts:526` (331): `errors: []` → `["Stryker was here"]` on the success path.** `nextOrMiss` reads `errors` only when `written` is none, and on this path it is some.
- **`progress.ts:619` (378): the "moved and came back" error's builder → `undefined`.** It is unreachable. `afterMiss` gives `refused` when the version is unchanged. Otherwise it gives `decide(now, transition)`, and here `transition.from`'s version is `before`, which is not `now`'s version. So `decide` returns the writer's own record or `PhaseMoved`, never `Succeed(none)`, and `landed` is never none.
- **`phases.ts:334` (307), `:590` (437): a `Context.Reference` key → `""`.** A key only has to be unique. Only one mutant is active at a time, and no other reference uses `""`. The timeout check re-ran 307 with a long timeout, and it survived: its wide-run Timeout was load.

### Noise (17)

All of it is text in an error, a refusal or a held item's title:

- `progress.ts` 73, 229, 237, 238, 313, 353–355, 357, 359;
- `ledger-check.ts` 46, 80, 82, 88, 127, 138, 190.

Test-observable string changes that aren't messages (the threads prefix, a work key, an activity's step name, a `catchTag`) are classified as real gaps, not noise.

## 4. Incremental state

Stryker keeps it in one JSON file, `reports/stryker-incremental.json` by default (`incrementalFile`). Here it was one file per target: 0.7 MB for progress and 1.0 MB for the catalogue. The file is a full mutation-testing report with test ids. On the next run, Stryker diffs each mutated file and each test file against it, and re-tests only:

- mutants whose code changed;
- mutants whose covering or killing tests changed;
- mutants with no `killedBy`.

The dry run always runs. Measured: 3.8–5.5 s with nothing changed, 4.1 s after a one-line edit.

**Carry it in `actions/cache`.** Use one key per module and night, `key: mutation-<module>-${{ github.run_id }}`, with `restore-keys: mutation-<module>-`. Caches are immutable per key, so this always restores the latest and saves a new one. A nightly job keeps it inside GitHub's 7-day eviction, and a few MB is nothing against the 10 GB limit.

The alternatives are worse:

- An artifact can't be downloaded from a previous run without a third-party action or `gh run download` plus run lookup.
- A state branch adds commits nobody reads, and would need its own ruleset.

A lost cache only costs one cold run.

Also upload `mutation.json` and `mutation.html` as artifacts each night, for people to read. Keep the state file in the cache only.

## 5. Exclusions

Measured noise is low (9%), so exclude little:

- **Ignore message text, not a mutator.** All 17 noise mutants are `StringLiteral` or `MethodExpression`s inside an error's or a refusal's message (`new XError({ message: … })`, `reason`, `fix`, `title`, `heldFor`/`recordNamed`). Turning `StringLiteral` off entirely would also hide real gaps found here: the `THREADS` prefix (71), the empty tree (74) and `catchTag("PhaseMoved")` (295, 385). Use a Stryker _ignorer_ plugin instead (Stryker 8+, `ignorers: [...]`), about 20 lines, that skips mutants inside the value of an object property named `message`, `reason`, `fix` or `title`.
- **Keep `ignoreStatic` off.** Static mutants found real gaps: `RUN_ID`'s anchors, the item-kind prefixes, `AWAITING_CI`'s anchors, `THREADS`. They are most of the cost when a selection has slow tests, which is one more reason to keep selections focused.
- **Keep `ObjectLiteral` on `Schema.Struct`.** It is mostly malformed-only, but not always: 387 (`reviewedBefore` on a record whose data lacks `reviewed` throws) and 416/417 (`itemOfWork` given the other kind's data) are genuine. Mark malformed-only ones ignored in the baseline, with a `// Stryker disable next-line ObjectLiteral: <reason>` comment, rather than excluding the mutator.
- **Settings for in-place runs:** `inPlace: true`, `disableTypeChecks: false` (Bun doesn't type-check, and it stops Stryker writing `@ts-nocheck` across the tree), `cleanTempDir: true`.
- **File patterns:** mutate only the files in scope (`mutate:` per module), never the fakes, tests or generated files. Each module's `testFiles` is an explicit list. No auto-discovery, and never `test/acceptance/`, per decision 2.
